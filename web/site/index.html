kibbr · a log store for structured JSON logs

Keep months of logs. Use a quarter of the disk.

kibbr stores each log line's shape once, in a trie, and its values as typed columns. Queries come back in milliseconds, from one static binary written in Rust. Scroll to see how a line is stored.

how a log line is stored
01

Logs arrive as JSON lines

Thousands a second, through POST /ingest. Each line is written to the write-ahead log and fsynced before kibbr answers 200. From then on it cannot be lost.

02

Every line is two things

Its shape: the set of keys. Its values: what this particular line says. Shapes repeat across millions of lines. Values are new every time.

03

Shapes go into a trie, in memory

A line's keys become a path. The next line with the same keys walks the same path, and nothing new is stored.

04

A new key branches off

A line with a different key set shares the beginning and branches at the end. Every leaf is a template, with its own columns on disk.

05

Values go to typed columns

Under their template, grouped by key: every timestamp in one column, every user in another. Thousands of rows to a group, one file per day.

06

Each column is squeezed its own way

Values of one kind sit together, so each column gets the trick that fits it: the gap from the row before, a word list, fewer bytes, or nothing at all when every row says the same thing. zstd goes over the result.

07

A query walks the trie first

It asks the trie which templates can match, then reads only the columns it needs. Most of the disk is never touched.

Measured, on an Apple M2

Small on disk. Quick to answer. Honest about the rest.

7.6%

of the original size on application logs, two thirds of gzip -9, and still queryable.

24.6%

on 1.5 GB of real GitHub events. gzip is smaller there: prose and 1,516 shapes cost kibbr. You can't query a gzip file.

0.16ms

to count one event across a million lines. Structured JSON only; no full-text search.
